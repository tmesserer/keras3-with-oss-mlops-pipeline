Part 1 · the map
Part 1 · vocabulary

Training and inference are two different jobs

Your course spends most of its time on the left box. This course is mostly about what has to happen around the right one.

Training

  • Reads 60,000 examples, many times over.
  • Takes minutes or hours, and needs a lot of computing power.
  • Starts, finishes, and stops. Nobody is waiting on the other side.
  • Produces one file: the trained model.

Inference

  • Reads one example: the one a user just sent.
  • Must answer in milliseconds, again and again.
  • Never stops. If it stops, something visible breaks.
  • Produces one answer, plus a line in a log.

One run is one training job: its settings, its scores, and the model file it produced. Part 1 does three runs, and serves one of them.

The two jobs have opposite needs. That is the reason Part 1 puts them in two separate boxes, and the reason the next slides are about boxes.
Part 1 · C1 and E1

You will evaluate the model twice, and the two are not the same

Evaluation after training

  • On a test set you kept aside before training.
  • You have the true answers, so you can count the mistakes.
  • It gives one number, and that number decides which run you ship.
  • It happens once, before anyone uses the model.

Evaluation after inference

  • On the real requests the running model answered.
  • Nobody wrote down the true answers. You only know what the model said, and how fast it said it.
  • It never stops, because the world does not stop changing.
  • It cannot give you accuracy. Not by itself.
So where do the true answers come from? In Part 1, from nowhere: you get a log file and your own eyes. Part 2 answers this question properly, by sending some decisions to a human being and storing the verdict.
Part 1 · B2, C1, C2

MLflow is two things: a logbook and a catalogue

  • The logbook. Every training run writes its settings, its scores and its model file into MLflow. Nothing is written on a sticky note.
  • The catalogue. Finished models are registered under a name, as numbered model versions: version 1, version 2, version 3.
  • The alias. An alias is a movable name. @champion points at exactly one version, and you can move it at any moment.
  • The server asks for models:/mnist-keras@champion and for nothing else. Moving the alias changes what is served, with no change to any code.

MLflow runs as a small web application on localhost:5000, so all of this is visible in your browser.

Part 1 · B1

Why any of this runs in containers

A container is a packaged, isolated environment: one program, plus everything that program needs to run, kept apart from your machine.

What you gain

  • The same environment on your laptop, on a colleague's laptop, and on a server. The famous sentence "it works on my machine" stops being a problem.
  • Nothing is installed on your laptop. Keras and torch never touch your own Python.
  • Two programs that need different versions of the same library can run side by side.
  • You delete the container and nothing is left behind.

Why two of them, not one

  • The trainer needs Keras, torch and the dataset. It is a large image, it works hard for a few minutes, and then it exits.
  • The server must start fast, stay up for days, and answer HTTP requests. It needs much less.
  • Different requirements, different images. Neither one carries the other's weight.
Part 1 runs three containers: MLflow, the trainer, and the server. Nothing trains inside your notebook. The notebook only gives orders.
Part 1 · B1

An image is a stack of read-only layers

  • An image is the packaged filesystem a container starts from. It is read only, and it never changes.
  • It is built in layers. Each instruction in the recipe adds one.
  • Layers are cached. Change train.py and only the top layer is built again. That is why the first build takes minutes and the second takes seconds.
  • Starting a container adds one thin writable layer on top. Stop the container, and that layer is gone. Anything you want to keep must be written somewhere else.
  • Images normally live in an image registry, such as Docker Hub. In this course your own laptop plays that role: you build the image and it stays local.

Part 1 · B2 and B3

The image is fixed. What you pass at launch is not.

  • The CMD is the command the container runs when it starts. It is written inside the image, and you can replace it at launch.
  • Everything that differs between two training runs is passed as an environment variable: a name and a value, handed to the program at the moment it starts.
  • You never rebuild an image to change a hyperparameter. Change the number, run the cell again. That is the whole edit cycle.
  • The same mechanism starts MLflow itself: its port, its database and its file folder are arguments, not code.

One training run — the trainer starts, trains, records the run, and exits.

docker compose --profile tools run --rm \
  -e RUN_NAME=cnn-32 -e KIND=cnn \
  -e SIZE=32 -e LR=1e-3 -e EPOCHS=5 \
  trainer

The next run changes two numbers. The image is untouched.

docker compose --profile tools run --rm \
  -e RUN_NAME=mlp-128 -e KIND=mlp \
  -e SIZE=128 -e LR=1e-3 -e EPOCHS=3 \
  trainer
Part 1 · the shared folder

A volume is a folder of yours, lent to a container

  • A container starts empty and forgets everything when it stops. A volume is how you give it a folder from your own disk that survives.
  • ./mlruns on your laptop appears as /mlruns inside every container, at the same address on purpose.
  • The trainer writes the model file there. The server reads the same file back. The two containers never speak to each other.
  • So you can delete every container and lose nothing. The runs, the models and the alias are on your disk.
Part 1 · A1 and A2

The dataset is deliberately easy

  • MNIST: 70,000 handwritten digits, 28 by 28 pixels, grey on black. 60,000 for training, 10,000 for testing.
  • The classes are balanced — about 6,000 examples of every digit. Accuracy is therefore an honest score, and you can choose a model with it.
  • In Part 2, only 0.58% of the rows are fraud. There, accuracy becomes a lie that reads as 99.6%.
  • Some digits are genuinely unclear, even to you. That is why a good score is 99-point-something and not 100.
When the data cannot surprise you, every surprise comes from the pipeline. The pipeline is the subject of this course.
Part 1 · D1, D2, E1

Serving is a normal web server with a model inside

  • An endpoint is one address that accepts a request and returns an answer. Here it is POST /predict.
  • Requests arrive as JSON: text. The model needs numbers of an exact shape: 784 pixels, arranged as 28 × 28 × 1, as decimals between 0 and 1.
  • Pydantic checks the request before the model sees it. A wrong length or a wrong type gets a clear error message, instead of a crash deep inside the model.
  • The server resolves @champion once, when it starts. POST /reload makes it look again, without a restart.
  • Every answer is appended to predictions.jsonl. That file is stage E, and Part 2 is built on it.
