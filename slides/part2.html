Part 2 · the stack

Eight containers need a written plan

A compose file is one text file that describes every container in a project, and how they fit together.

  • Part 1 ran three containers, and you started them one at a time. Part 2 runs eight.
  • The file names each service: which image, which ports, which environment variables, which volumes.
  • It also creates a private network. Services find each other by name, so mlflow-server is an address.
  • depends_on sets the start order. A profile is a label, so --profile part2 starts one part and leaves the other alone.
  • One command starts all of it, and one command removes it again. Nothing else is installed on your machine.
services:
  fraud-serve:
    image: keras-mlops-fraud-serve
    ports: ["8001:8001"]
    environment:
      MLFLOW_TRACKING_URI: http://mlflow-server:5000
      POSTGRES_DSN: postgresql://…@postgres/mlops
    volumes: ["./mlruns:/mlruns"]
    depends_on: [mlflow-server, postgres]
    profiles: ["part2", "serve2"]
You already know what a container is. Compose adds no new idea — it is the written plan for many containers at once, kept in git beside the code.
Part 2 · the stack

What a business would use instead

Compose runs containers on one machine, and assumes somebody is watching. Kubernetes is the standard tool for the case where nobody is.

What it adds

  • It restarts what dies. A container that crashes at three in the morning comes back without you.
  • It runs many copies. Ten copies of the endpoint behind one address, with the traffic shared between them.
  • It updates without downtime. A rolling update replaces copies one by one, and returns to the old one if the new one fails.
  • It chooses the machine. With fifty servers, deciding where each container runs stops being something a person can do.

What does not change

  • The same images you built here. The same environment variables. The same registry, the same database.
  • Cloud or your own building: Kubernetes runs in both. Banks in Luxembourg run it on their own hardware.
  • Only the thing that starts the containers changes. Everything this course teaches sits above that line.
This course stays on one laptop on purpose. You are learning the loops, not the hosting. The loops are the part that transfers.

Part 2 · A data · A2 look before modelling

Four facts about the data decide everything that follows

172 normal for every fraud

A model that always answers "not fraud" is 99.6% accurate and completely useless. So accuracy cannot choose your model, and training must give the rare class extra weight.

The same cards come back, again and again

A fixed set of cardholders and 693 merchants, over two years. Every card therefore has a history here, and "unusual for this card" would be strong signal. Amount, hour and category separate fraud without it — which is what makes scoring one row at a time possible at all. Slides 7 and 8 return to what that choice costs.

The fraud rate falls over two years

The world changed while the data was collected. Change like this is called drift. A model that was right in 2019 is less right in 2020, and no code will tell you.

The split is by time, not at random

The test file begins 48 seconds after the training file ends. Shuffle the two together and you train on the future to predict the past. That is leakage: every score you report then looks excellent and is wrong.

And the fact the whole second half of this deck rests on: is_fraud is a column in this file. In production that column does not exist.
Part 2 · B train · B2 the threshold

PR-AUC chooses the model. A person chooses the threshold.

  • Accuracy sits at 0.998 while the model misses a third of all fraud. It is logged on purpose, so that you can watch it lie.
  • PR-AUC is the score that decides the champion. It asks two questions only. Of the transactions you flagged, how many really were fraud? And how much of the fraud did you find?
  • At a base rate of 0.4%, a random model scores 0.004 on PR-AUC and 99.6% on accuracy. Only one of those numbers teaches you anything.
  • The model does not output a decision. For each transaction it outputs P(fraud), between 0 and 1. The threshold is a cut on that number: at 0.62, a transaction is declined when the model puts its chance of fraud at 62% or higher. It is not 62% of the transactions.
  • Choosing that threshold is a business decision, not a modelling one. It trades declining good customers against letting fraud through, and no library can make that trade for you.
  • The trainer chooses the decline threshold on the validation data — the slice it held back while training — and never on the test set. It writes that number onto the run as a tag.
# tags on the run, in MLflow
test_pr_auc          0.781
accuracy             0.998   ← varies by a rounding error
operating_threshold  0.62   ← decline at P(fraud) ≥ 0.62
dataset_md5          3f2a…c81

The threshold belongs to the model, so it travels with the model and is promoted with the model. It is the contract between the trainer and the server.

Part 2 · A data · A3 the features file

From one row of the file to the numbers the model reads

A row is text, dates and coordinates. A neural network reads numbers. common/features.py converts one into the other.

  • A timestamp becomes an hour and a weekday. Fraud keeps different hours from normal shopping.
  • A date of birth becomes an age in years, counted at the moment of the transaction.
  • Two pairs of coordinates become one distance. The card's home and the merchant, in kilometres. Fraud tends to happen far away.
  • An amount becomes two numbers, itself and its logarithm: amounts are heavily skewed, median 47 against a maximum of 28,949.
  • A name becomes a bucket number. 693 merchant names go through a checksum into one of 2048 buckets, and no list of names is stored anywhere.
one row in            what the model receives
trans_..._time 22:32  hour 22 · dayofweek 6
dob 1968-03-19        age_years 52.3
lat,long + merch_...  distance_km 78.4
amt 780.52            amt 780.52 · log_amt 6.66
category "misc_net"   category 11 of 32
merchant "Kozey-..."  merchant 1663 of 2048

Seven numbers and four buckets, built from one row and nothing else. This is the whole of the feature engineering in Part 2.

Notice what it never does: it never learns. No average and no vocabulary is computed here. Every transform that depends on statistics lives inside the Keras model, so the model in the registry is complete on its own — one artifact, with nothing to ship beside it.
Part 2 · A data · A3 two rules, and what they cost

Both sides import that one file, and neither may look at history

Rule 1 · one copy, imported twice

  • In Part 1 the server never imported the trainer, and that separation was the point. Here they share one file, deliberately.
  • The alternative is writing the date parsing and the distance a second time, in the server. The two copies then slowly stop agreeing.
  • Training would prepare its inputs one way and serving another. That is training/serving skew: no error, no warning, and a model that tested well failing quietly in production.
  • The price is real. Editing this one file changes both sides at once, and makes every model already in the registry invalid. Nothing in the registry records which version of that file built a model's inputs.

Rule 2 · every feature uses one row

  • No "average spend over the last 30 days" — even though the file does hold each card's history, as slide 5 said.
  • The endpoint receives one transaction and knows nothing about earlier ones. It cannot compute an average it has never seen.
  • Features built from history need a feature store: a service that keeps those running totals up to date, and gives training and serving the same values. Real fraud systems have one.
  • This project does not build one, and leaves the boundary visible instead of hiding it behind a feature that quietly uses the future.
Both rules exist for the same reason: what the model sees during training must be exactly what it sees in production. Rule 1 protects that across two containers. Rule 2 protects it across time.
Part 2 · C serve · C2 the decision band

Three answers, not two

  • threshold_decline is the operating point the trainer chose. threshold_review sits below it.
  • Between the two the model is unsure. A transaction there is not approved and not declined. It is set aside for a person.
  • That middle band is not a decoration. It is the sampling strategy for the whole of loop ②, and the reason the review queue produces labels worth paying for.
  • If a model version carries no threshold, and no override is set, the server refuses to start.
  • Defaulting to 0.5 would be easy. At this base rate it would decline a large share of honest customers, and it would do it silently. A service that will not start is a much better failure than a service that starts wrong.
Part 2 · D consume · D1 the application

A simulated business application, so that something depends on you

  • txn-app replays the test file at the endpoint as a live stream, and shows what is happening on a dashboard.
  • Nothing about it is realistic except the part that matters. It is a program that cannot continue without an answer.
  • With curl you are a patient human. An application is not patient, and it has its own users waiting.
  • It contains no machine learning at all: no keras, no torch, not even the features file. Its image is about 100 MB.
  • That rule is a test you can run. If this application ever needs an ML library, the serving boundary has leaked.
  • Because it is simulated, you may break it on purpose, at any moment, with nobody losing money. That is the next slide.
Part 2 · D consume · D2 breaking it

Now point the application at an address where nothing answers

No container is touched. The client side of a completely realistic failure, entirely under your control.

1 · timeout and retries

  • A transaction waits two seconds, and asks at most twice more.
  • Waiting for ever is not an option. Somebody is standing at a checkout.

2 · fallback

  • Every transaction still needs an answer. An unscored one gets the fallback decision.
  • approve loses money to fraud. decline turns away good customers. review fills a queue no human can empty.

3 · circuit breaker

  • After five failures in a row the circuit opens: requests are answered from the fallback, with no call made at all.
  • Every ten seconds one request is allowed through, to test whether the endpoint is back.
The name is borrowed from the switch in your house. It cuts the current so that one fault does not burn the building. There is no free option here, and somebody has to own the choice before the outage, not during it.

What a dead endpoint costs, in milliseconds and in euros

The cheapest line is a trap: analysts clear about two transactions a minute, so "review all" buys ten minutes of calm with fifty hours of backlog. A dead dependency does not only fail your requests — it holds your program while failing them, and the outage then spreads into services that were healthy.

Part 2 · E review · why it exists

What you cannot know without a human in the loop

In the file, the answer was in the column next to the transaction. In production, nobody writes it down at all.

Without verdicts, this is your situation

  • The model says 0.91, the transaction is declined, and the world says nothing back. Ever.
  • You cannot measure precision or recall on live traffic. You only know what the model said, and how fast it said it.
  • Drift becomes invisible. The fraud rate moved across the two years in your file. Live, nothing would show you that it moved again.
  • Retraining has nothing new to learn from. You would train again on the same old labels, and call the result an improvement.
  • The model's own confidence is not evidence. A wrong model is often a confident one.

A verdict is the missing measurement

  • One analyst decision turns one live transaction into a labelled example.
  • With enough of them you can finally count today's mistakes, and not only the mistakes on a test set from two years ago.
  • Those same labels are the training data for the next model. Loop ② feeds loop ③.
  • And the analyst sees cases the model found hard, which is exactly where a new pattern of fraud appears first.
This is the honest end of Part 1. The log file records what the model answered. Nothing in Part 1 records whether it was right.
Part 2 · E review · E1 choosing what to send

Labels are not data you have. They are data you buy.

  • Every label costs an analyst's minutes. The budget is small, so the real question is which transactions you send them.
  • The first plan for this project was "sample 1% at random". At a 0.4% fraud rate, a random sample is almost entirely obvious legitimate traffic. You pay for a hundred labels and learn from one.
  • The review band sends the cases where the model is unsure. A human verdict there carries information the model does not already have. This is called uncertainty sampling.
  • The queue is sorted by probability, highest first. A half-finished queue is therefore always the half most worth finishing.
  • The width of the band is a budget decision. Wider band, more labels, more analyst hours.
Part 2 · E review · E1 the tool

Before you install anything: build the review tool yourself

You need a screen where an analyst decides "fraud" or "legitimate". How hard can it be? Write the list.

What that screen actually needs

  • A login, and one account for each analyst.
  • A queue that never hands the same transaction to two people.
  • Buttons a person can press two hundred times an hour without hating you, and keyboard shortcuts, because the mouse is the slow part.
  • A record of who said what, and when: an audit trail.
  • The same case given to two analysts sometimes, to measure whether they agree with each other.
  • An API, so your pipeline can add tasks and read verdicts back.
  • A webhook: a message the tool sends to your service the moment something happens.
That is a product. It is months of work, it is nobody's idea of machine learning, and it is not the product your employer is paying you to build.

So you install one

  • Label Studio CE is that product: open source, Apache-2.0, storing its data in the same Postgres, running on your laptop with no account anywhere.
  • You spend an afternoon on a configuration file instead of a quarter on a user interface.
  • The original plan for this project named a different tool and described it as self-hosted. It is not: it is sold as a service only. Read the licence before you design around a tool.
Part 2 · E review · E2 the wiring

The queue is not the system. The wiring is.

  • label-sync is a small service with one job: move rows between Postgres and Label Studio. It has no ML dependency, exactly like the application.
  • Outward, every 30 seconds: sweep the review band and push whatever is not queued yet, highest probability first.
  • Back, by two paths on purpose. The webhook is the fast path, sent the moment an analyst saves a verdict.
  • POST /pull re-reads every annotation from the API. This is the path that matters. A webhook is sent once and never checked, so a delivery lost while the service restarted is invisible.
  • The annotation still exists, the analyst was still paid, and nothing would ever notice it was missing. A label that was bought and thrown away is the worst outcome in this system.
  • Both paths upsert: insert the row, or update it if it is already there. So replaying costs nothing, a corrected verdict overwrites cleanly, and nothing can be counted twice.
And one thing the task must never show: the model's score. The analyst sees the amount, the merchant, the category, the distance and the cardholder. Nothing else.

An analyst who reads "0.97 — DECLINE" agrees with the model. A queue that only confirms produces labels with no information in them, and those labels then teach the next model to make the same mistakes with more confidence. The score decides what gets reviewed. It must not decide the answer.

Part 2 · E review · what it costs

Adding a human is adding a second system

The review loop removes a blind spot. It also creates an operation that somebody has to run, for ever. Both are true.

Money and time

  • Every label has a price, and the budget decides the width of the band — not the other way round.
  • A verdict arrives hours or days after the decision. Your ground truth is always about the past.

People

  • Two analysts label the same case differently. You need a rule for that, and a number for how often it happens.
  • A queue that is too full gets ignored. An empty one wastes a paid person. Somebody owns the queue.

New failure modes

  • The band decides what humans ever see, so the next model learns from that slice and not from the world.
  • If the queue stops, nothing breaks visibly today. Your labels simply stop arriving, and you find out much later.
Budget for the second system before you promise the first. "We will add human review later" is a plan for a team, not a line in a sprint.

Part 2 · F version · F1 what a hash is

You have used hashing already, twice

A hash function reads bytes and gives back a short string. The same bytes always give the same string. One byte different gives a completely different one — there is no "almost the same".

Every set and every dict in Python

  • x in some_set answers at once on a million items. x in some_list reads them one after another until it finds x.
  • The set never searches. It hashes x, and the string says where x would have been stored. It looks in that one place — which is also why d["merchant"] costs the same in a dict of ten keys and one of ten million.
  • And why a list cannot be a dict key: its contents can change, so its fingerprint would not stay where it was put.

Every large file you have downloaded

  • Hugging Face and Kaggle publish a checksum beside each file. A checksum is a hash of the bytes they hold.
  • When your 5 GB download ends, the tool hashes what arrived and compares the two short strings. Equal: nothing was lost on the way. Different: throw it away and ask again. Nobody compares 5 GB byte by byte.
  • Hugging Face goes further and stores each file under its own hash as the name, so asking twice for the same file downloads it once.
# 1,296,691 rows. In the second file, one of them has one cent more.
fraud_training.parquet            cf7b9955942cc36a68c45d90972263f4
fraud_training.parquet  (edited)  b89fd6f606db11cc23404f2cd7a98dd4
A fingerprint that can tell you a download arrived intact can tell you a training set is the one you trained on last month. Same tool, new job.
Part 2 · F version · F1 the file format

Parquet, and why the file must be written the same way every time

What parquet is

  • A file format for tables. CSV is text: every number is written out as characters, and every reader has to guess the types again.
  • Parquet keeps each column together, in binary, compressed, with the type recorded inside the file.
  • Smaller and much faster to read. Here: 84 MB, against about 500 MB of the same rows as CSV.
  • A person cannot read it in a text editor, which is fine. A program reads it.
# part2/pipeline/build_dataset.py
df = df.sort_values(["trans_date_trans_time", "trans_num"],
                    kind="stable")
df.to_parquet(OUT, index=False)

Same rows in, same bytes out, today and in November. Nothing that moves on its own is allowed into the file: no row numbers, no build timestamp, and no "in whatever order they arrived".

$ md5sum data/derived/fraud_training.parquet
cf7b9955942cc36a68c45d90972263f4  fraud_training.parquet

Build the file again tomorrow from the same rows and this command prints the same 32 characters. It is also exactly the number DVC keeps in git, which is the next slide.

The fingerprint is of the file, not of the data. An unstable sort would change the fingerprint without changing a single value — every rebuild would then look like new data, and the versioning would mean nothing at all.
Part 2 · F version · F1 and F2 the snapshot

A dataset that can be named

Code has git. Models have the registry. Data usually has "the file on the shared drive that someone regenerated in March".

  • DVC puts a small text file in git — 106 bytes — that names an 84 MB file by its fingerprint. The big file itself stays out of git.
  • The trainer reads that pointer and stamps the fingerprint onto the run. Any registered model can be traced back to the exact bytes it learned from, and not to a filename that means something different next month.
  • If the snapshot is missing, the trainer falls back to the raw CSV and tags the run dataset=raw-csv. The provenance — the record of where the data came from — is never absent. It just tells a different story.
  • The snapshot keeps the reviewed transactions out of the test set. They come from the test period, so training on them and then scoring on the whole file would be leakage all over again.
  • The pipeline only verifies this fingerprint. It never rebuilds it, because a pipeline that rewrites a pointer nobody read would version data by accident.
# data/derived/fraud_training.parquet.dvc
# 106 bytes, committed to git
outs:
- md5: cf7b9955942cc36a68c45d90972263f4
  size: 84098264
  hash: md5
  path: fraud_training.parquet

Git tracks the pointer. The parquet file lives beside it, ignored by git, rebuilt by a script. One line in a commit now answers "which data was that?" for ever.

Part 2 · G orchestrate · what Airflow is

An orchestrator is a shift manager with a notebook

  • A DAG — a directed acyclic graph — is a list of tasks plus the order they must run in. Directed: every arrow points one way. Acyclic: the arrows never close into a circle, so no task can ever wait for itself.
  • Think of a recipe. Boiling the water and chopping the vegetables can happen at the same time. Serving cannot happen before either of them. That shape is a DAG.
  • Airflow is the shift manager. It starts each task when the tasks before it have finished, keeps every log, retries what failed, and shows you which step is red.
  • A DAG runs on a clock, or only when a person presses the button. Both are normal.
  • It does not do the work. The training task starts the very same trainer container you started by hand. An Airflow image carrying keras would be a second place for the training environment to drift.
Airflow arrives last in this course and automates nothing new. Build the orchestrator first and you debug a scheduler instead of a pipeline, and you finish with steps nobody ever proved by hand.
Part 2 · G orchestrate · G1 and G2, the two DAGs

Two DAGs, two schedules, and a promotion that may refuse

sync_labels · every 15 minutes

push → pull → report

  • On a clock, because labels arrive continuously.
  • It exists mostly for the pull: it recovers the verdicts a lost webhook dropped.
  • "We should re-read those sometimes" becomes something the system does, not something you remember.

fraud_retrain · when you press the button

check_snapshot → train → promote → reload_serving

  • No schedule at all. A fraud model does not retrain on a calendar; it retrains when the data has moved.
  • Deciding that it has moved is still a human's job.
  • Each task wraps a cell you have already run by hand. check_snapshot only verifies the parquet fingerprint against the pointer in git; it never rebuilds it.
  • promote compares before it moves anything: the run must have used this snapshot, its files must really be on disk, and it must beat the champion's PR-AUC. Otherwise the task skips and the alias stays where it is. A retraining pipeline that always promotes is not a pipeline, it is a liability.
  • reload_serving is where the loop closes. Promotion alone changes nothing, because the server resolved the alias when it started.
On the dashboard you then see two model versions inside the same minute. That is the exact request where the model changed, under a stream of transactions that never stopped.
Part 2 · what to take to work

You do not need all of this to get value from any of it

Read from the bottom. Every rung is useful on its own, and each one is worth adding only once the rung below it hurts.

Part 2 · why a bank cares

Six questions an auditor asks, and the record that answers each

Rules differ by country and by sector, and this is not legal advice. The pattern behind them is always the same: show your work.

"Which model made this decision?" the model version is stamped on every row in scored_transactions "When did the model change?" the registry keeps numbered versions; moving @champion is a recorded event "What data did it learn from?" the run carries the dataset fingerprint, and the fingerprint names exact bytes "How has it performed since it went live?" the telemetry tables, plus the verdicts that arrive later as ground truth "Where is the human oversight?" the review queue: a named analyst and a timestamp on every verdict "Can you reproduce it?" same image, same environment variables, same data fingerprint
Not one of those answers required extra work for the auditor. They are by-products of the loops — which is the argument for MLOps that a finance employer understands fastest.

Written records of this kind are what the EU AI Act asks of a high-risk system, what model-risk rules have asked of banks for years, and what your own colleague asks when a decision is questioned six months later.

Part 2 · the next thing you will be asked for

Where a large language model plugs into this same loop

The boxes change. The loops do not.

What changes

  • You did not train the model, so the prompt is the thing you version. Keep it in git and stamp it on every call.
  • Pin the model name and its date. Providers change what sits behind a name, and your results move without you.
  • The test set becomes an evaluation set: examples with expected answers, run on every change to the prompt.
  • Telemetry gains two columns: money per call, and tokens. A model that is 2% better and five times dearer is a business decision again.

What is exactly the same

  • A confidence band that routes the uncertain cases to a human.
  • A queue where that human answers, and a table where the answers land.
  • A consumer that must survive the endpoint being slow or absent — and LLM endpoints are slow and absent far more often than this one.
  • A record of which version answered, when, and on what evidence.
In this project the honest place for one is writing the analyst's case summary from the transaction history — helping the human decide, not making the decision. Everything you have built around the fraud model is what would make that safe to run.
